# 来源收集与覆盖

## 单个对话

直接使用用户指定的当前对话或导出。仅在用户明确要求跨对话回顾时扩展到其他任务；不因为缺少项目就要求创建项目。不具备历史访问工具时，以用户提供的文本和实际可见范围为准。

## 生成前的覆盖检查

每次首次采集或补收聊天都执行以下检查。UI 刷新且材料范围不变时可沿用已有回执，明确“未重新采集”，不能据此升级覆盖结论。

1. **明确范围。** 记录项目／对话 ID、已知目录及时间边界。用户要求整个项目时，检查与它相关的活动和归档聊天；读取元数据判断归属，不读取无关聊天正文。已知旧目录、旧项目名及材料中明确引用的聊天 ID 都纳入查找线索。搜索关键词只帮助发现，不能证明列表完整；只有日期接近或标题相似不足以合并。
2. **列全候选。** 翻完任务列表的分页；记录返回的继续游标及实际终止条件。列表按更新时间排列时，不因一页里出现旧日期就停止。不支持归档或分页时记为发现范围受限，不能记作零条。每个候选都有处理结果：纳入、附依据排除或归属未确认；不能静默丢弃。
3. **读完范围。** 对每个纳入对话继续读取其轮次分页，直到工具证明范围结束。保留原始消息 ID 和角色；仅提取用户消息与助手公开回复，避免把工具输出或推理混入阅读器。读取超限时用工具支持的较小批次／输出选项继续；同一最小请求仍失败就记录具体未读范围和错误，不无限重试。没有原始 ID 的文本按真实行号／消息序号检查到文件结尾；压缩摘要不等于读完原对话。
4. **分开记录检查与展示。** 在输出目录维护简短的 `source-audit.md`：范围、发现来源与分页终点、候选总数及各自处理结果、纳入对话的读取状态（完整／部分／不可访问）、未读位置及原因、导出位置。另记页面保留全部原文还是只选取摘录。读取完一轮后只保存其中关键消息，可以记“已检查、展示为摘录”，不能记“全部原文已收录”。不复制完整工具响应、隐藏推理或凭据到回执。
5. **双向核对。** 对照候选清单，确认每个纳入对话都进入来源记录，或有明确的不展示理由。再核对节点：精确关联、仅候选、无摘录分别计数；没有摘录的阶段回查已知原任务、旧名称和原始文档中的明确线索。真实摘录与模块尚未建立关联时补关联；没有证据时保留缺口，不为提高数字任意挂接。
6. **交付前判定。** 有待取分页或未处理候选且工具仍可用，继续查找后再作最终交付。确实受限时可以交付部分版本，但首次交付就说明受限来源、范围及原因。只有发现范围明确、所有候选已处理且纳入对话全部读完时，才能说“指定范围内可访问的对话已检查完”；是否保留完整原文另行报告。不能承诺所有平台、账号、已删除对话或未获访问权的历史都已找齐。

回执使用实际工具结果填写；未记录的分页终点或读取状态写“未知”，不能为通过检查倒填“完整”。Codex 历史工具可用时，必须采用 [自动采集器](automatic-collection.md) 生成检查点、导出和机器可校验回执；打包器会核对分页与文件一致性。检查仍不能证明工具未列出的聊天不存在。

为控制 token，用 ID 去重并在本地保存一次原始公开消息，后续提炼按章节引用消息 ID；同一长轮次关联多个模块时复用已有摘录。续做时读取回执，从未完成游标继续；更新时先检查范围内是否新增／修改了对话，再读取变化部分，不重复总结所有旧记录。不能以减少 token 为由把尚未读取的部分标为完成。

## Codex

工具名以宿主实际提供为准，列表只帮助定位，不代表完整历史。

1. 用项目 ID、指定任务 ID/标题、时间范围定位候选。不自动合并同名或时间接近的任务。
2. 用 `read_thread` 阅读选定任务。需要文件路径、测试结果、原因时请求相关输出（工具支持时用 `includeOutputs`）。截断则补读，不把截断内容当全文。
3. 任务列表与单个任务的轮次列表都要检查分页。历史较长时，按指定项目和时间范围继续 `list_threads(mode="history", cursor=...)`，不能只读最近一页就认定早期聊天不存在。选定任务再用 `read_thread` 的 cursor 补取相关旧轮次。没有分页、读取超限或达到预算时记录实际覆盖；有限列表不等于项目全部对话。
4. 仅在范围需要时检索归档任务，不恢复或修改。不向任务发送消息，不用公开分享工具生成引用链接。
5. 记录工具实际返回的稳定 ID、原文标题、时间及轮次。没提供可跳转 URL 时省略 `uri`，用文字定位。

当前对话可以是独立 source。只有压缩摘要则 `coverage=summary`；不制造精确原话、轮次或丢失的决策。

用于对话阅读器的导出仅保留相关用户消息与助手公开回复／进度，不收录隐藏推理或工具输出。一个长轮次涉及多个模块时，优先用消息 ID 定位各模块的实际回复；只有任务 ID 不能视为阶段精确关联。助手的公开进度仍是当时陈述，不能据此声称本次重新验证了项目。

## 导出及补充材料

记录提供者、原文件/链接和读取范围。大文件先检索再读上下文，不能只凭命中行解释决策。重复导出优先按稳定消息 ID、其次按内容与时间去重。时间不明可记录相对先后，不虚构日期。

文档/Git/测试日志可补证事实。聊天提议、AI 自述完成、文件存在、提交和通过测试是不同证据，在 `note` 说明。

## 链接

一起交付的文件优先用相对于 `evolution.json` 的相对路径。绝对路径仅适用于原机器；浏览器可能限制文件链接，页面保留原路径供复制。不要为生成图重跑产物或旧代码，也不自动复制全部产物。

远程链接默认不预取，不自动登录或公开分享。`unchecked` 不等于失效；`missing` 需要实际检查。保留回溯所需的最少短摘录。用户要求可分享版本时另制脱敏副本，不覆盖原始证据。


## 对话覆盖验收

图中有阶段不代表已取得对应聊天。分别统计精确关联、同来源候选、无关联节点，并说明缺口来自未收录还是未建立关联。逐项核对已保存的多模块请求／交付：明确涉及多个 Feature 的同一轮可关联多个节点，标明共享轮次，不能只挂在最后一个 Feature。保留已有文档/Git补证；没有聊天原文的阶段明确标为缺失，不生成模拟问答，也不把后续提到旧功能的消息当作旧功能开发对话。


## 人工关联与缺失原文

页面允许用户把真实已保存轮次关联到一个或多个模块，人工标记独立保存，并与原记录精确关联区分。仅同来源的候选不计入确认关联。人工导航标记不等于取到原始开发问答，也不会把摘要升级成完整聊天。导出／导入的关联 JSON 只迁移标记；缺失原文仍须定位原任务或取得相应导出后再整理。不要为覆盖率更高而随意选择无关摘录。
